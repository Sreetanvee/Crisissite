# Disaster Intelligence & Human Review Platform

A decision-support prototype for **simulated flood** impact assessment. It fuses satellite/aerial
imagery, weather data, sensor readings, and incident reports into a transparent, explainable
"Multimodal Evidence Score," surfaces the most important zones for a human operator, and lets that
operator inspect every piece of underlying evidence before doing anything.

> **This system never makes autonomous operational decisions.** Every score, every priority ranking,
> and every summary is explicitly labeled as requiring human review. This is enforced throughout the
> UI (a persistent warning banner) and in the data model (every detection carries a status and
> confidence that flags low-confidence or conflicting results for mandatory review).

---

## 1. Architecture

```
Weather + Sensors + Incidents + Satellite imagery
                    │
                    ▼
      app/services/fusion.py  (transparent weighted scoring)
                    │
                    ▼
        Detection record (score, confidence, status, priority)
                    │
        ┌───────────┼────────────┐
        ▼           ▼            ▼
   Review Queue   Zone Detail   Timeline
   (prioritized)  (evidence)    (Recharts)
```

- **Frontend**: React + Vite + Tailwind CSS, React Router, React-Leaflet (map), Recharts (charts).
- **Backend**: Python + FastAPI + SQLAlchemy + SQLite.
- **ML layer**: a lightweight, explainable heuristic image classifier (color-index water detection,
  `app/ml/image_analysis.py`) plus a transparent weighted multimodal fusion formula
  (`app/services/fusion.py`) — no GPU, no external model downloads required.

### Why a heuristic instead of a trained deep learning model?

The brief explicitly asks us not to claim a complex model was trained if it wasn't, and to keep the
ML lightweight enough to run on a normal laptop with no GPU. Rather than fake a "trained CNN," this
MVP implements a real, if simple, remote-sensing technique: a color-index water detector that looks
at blue/green dominance, brightness, and saturation to estimate how much of an aerial tile looks like
turbid flood water. It runs on genuine pixel data — swap in real satellite tiles and it produces a
real (if simplistic) result. The code is structured so a real trained segmentation/classification
model can be dropped into `app/ml/image_analysis.py` behind the same `analyze_flood_tile()` interface
without touching anything else in the pipeline.

## 2. Dataset

All data shipped with this repo is **clearly labeled DEMO / SIMULATED data** (`is_demo=True` on every
row, and a "DEMO DATA" badge shown throughout the UI). It is generated once, deterministically, by
`app/services/seed_data.py` on first backend startup, and includes:

- 10 geographic zones (Hyderabad-area coordinates, used only as a plausible demo backdrop)
- 50 sensor readings and 50 weather readings (5 timestamps × 10 zones)
- 11 incident reports
- 15 synthetic aerial tiles, procedurally generated by `app/ml/image_generator.py` and then actually
  analyzed by the real heuristic classifier (the `flood_probability` values are computed, not typed in)
- 50 fused `Detection` rows (one per zone per timestamp), each produced by actually running the fusion
  engine — nothing here is hand-authored

The dataset is internally consistent: rainfall and water level ramp up over the simulated day in
proportion to each zone's target severity, incident reports appear only after conditions have
worsened, and the fusion score/priority/confidence for each zone rises accordingly across the
timeline.

**To use real data instead:** point `app/services/seed_data.py` (or a new ingestion script) at real
CSV/JSON weather and sensor feeds and real image tiles, write them into the same SQLAlchemy models,
and run them through the same `app/services/fusion.py` pipeline. No other code needs to change.

## 3. Preprocessing

- Satellite tiles are read as RGB arrays with PIL/NumPy; no resizing/normalization pipeline is needed
  at this scale, but `image_analysis.py` is the natural place to add tiling, cloud masking, or
  reprojection for real satellite products.
- Weather and sensor values are used as raw physical units (mm, °C, %, km/h, meters, m/hour) and
  converted to 0–1 "scores" only inside the fusion step, so the raw evidence is always shown alongside
  the derived score.

## 4. Model

- **Image**: heuristic color-index water/flood detector (`app/ml/image_analysis.py`). Outputs a
  `flood_probability` (0–1) and an `analysis_confidence` (0–1) per tile.
- **Fusion**: a transparent, explainable weighted combination (`app/services/fusion.py`):

  ```
  Multimodal Evidence Score =
      100 × ( 0.40 × image_score
             + 0.25 × rainfall_score
             + 0.25 × sensor_score
             + 0.10 × incident_score )
  ```

  If a modality is missing, its weight is redistributed proportionally among the modalities that
  *are* present (never silently treated as zero or ignored), and the result is flagged
  `LIMITED_EVIDENCE`. If present modalities disagree strongly (max pairwise gap ≥ 0.40 on a 0–1
  scale), the result is flagged `CONFLICTING_EVIDENCE`. If overall confidence drops below 60%, the
  result is flagged `LOW CONFIDENCE — HUMAN REVIEW REQUIRED`. All of this is visible in the UI, not
  just logged.

## 5. Evaluation

See `app/services/evaluation.py` and the **Model Evaluation** page. There is no real, independently
labeled flood dataset behind this MVP, so evaluation is run against a **synthetic, internally
generated held-out test set** with known ground-truth labels baked in at generation time. The
pipeline then actually runs the real classifier and fusion logic against that test set and computes
accuracy / precision / recall / F1 / confusion matrix with scikit-learn — every number shown is a real
computed output, not a fabricated one, but it describes performance **on synthetic data only** and
must not be read as real-world performance. This is stated explicitly on the Evaluation page and in
the API response.

Three variants are compared: image-only baseline, weather/sensor-only baseline, and the full
multimodal fusion.

## 6. Limitations

See the in-app **Dataset & Limitations** page for the full list (geographic limitations, sensor
coverage, class imbalance, false positive/negative modes, temporal mismatch between modalities,
regional bias, etc.).

## 8. Setup & run instructions

Requires Python 3.10+ and Node.js 18+.

### Backend

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

The database is created and seeded with demo data automatically on first startup
(`backend/data/disaster_intel.db` and `backend/data/satellite/*.png`). Delete
`backend/data/disaster_intel.db` and restart to re-seed from scratch.

API docs (interactive): http://localhost:8000/docs

### Frontend

In a second terminal:

```bash
cd frontend
npm install
npm run dev
```

Open http://localhost:5173. The Vite dev server proxies `/api` and `/static` to the backend on port
8000 (see `vite.config.js`), so both must be running.

### Production build (frontend)

```bash
cd frontend
npm run build
npm run preview     # serves the built app locally for a final check
```

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/events` | List disaster events |
| GET | `/api/zones` | List zones (optional `event_id` filter) |

| GET | `/api/review-queue` | Prioritized human review queue |

| POST | `/api/analyze?zone_id=` | Re-run fusion for a zone against its latest readings |
| GET | `/api/evaluation` | Model evaluation metrics (image-only, weather/sensor-only, fusion) |

## 10. Implementation notes

- Every dashboard number is backed by an actual database query or an actual computation — nothing
  displayed is hardcoded while pretending to come from a model.
- Every satellite `flood_probability` value is the real output of `analyze_flood_tile()` run against
  an actual (synthetic) image file, not a typed-in number.
- Every evaluation metric is the real output of scikit-learn run against actual predictions vs. known
  synthetic labels, not a fabricated number.
- Missing-modality and disagreement handling is implemented, not just documented (see
  `run_fusion()` in `fusion.py`).
- Wildfire detection is explicitly out of scope for this MVP, per the brief.
